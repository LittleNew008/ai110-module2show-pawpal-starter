## Agent Workflow (SF7)

> Document your experience using an AI agent (e.g., Cursor Agent, Claude, Copilot) to make multi-step changes autonomously.

**What task did you give the agent?**

Design the main objects for the PawPal+ pet care app described in the README (what each holds and what actions it performs), then turn the design into a UML diagram and Python class stubs. Follow-up decisions: plans use clock times, and a required task that does not fit is flagged. Also asked it to keep this log and `reflection.md` updated at each interaction.

**What did the agent do?**

1. Read `README.md`, `app.py`, `diagrams/uml.mmd`, `reflection.md`, and `ai_interactions.md` (read-only, in plan mode).
2. Proposed the objects (Owner, Pet, Task, Scheduler, DailyPlan, ScheduledItem) with their data, actions, relationships, and edge cases, and saved the plan.
3. After approval, wrote the Mermaid UML in `diagrams/uml.mmd`.
4. After the two design decisions, created `pawpal_system.py` (dataclass and enum stubs, no logic), added `flagged` / `flagged_tasks()` to the UML, and filled in `reflection.md` and this file.
5. Asked to produce the Mermaid class diagram from the brainstormed attributes and methods. The agent rewrote `diagrams/uml.mmd` to match the stubs (renamed `DailyPlan.date` to `on`, added the missing `ScheduledItem`/`SkippedTask` to `Pet` links). It had no Mermaid CLI, so it replaced nested generics such as `list~tuple~Pet, Task~~` with plain-text return types to avoid a likely parser error. The diagram has not been rendered.
6. Asked to double check `pawpal_system.py` against `diagrams/uml.mmd`. The agent read both, then wrote a throwaway script that parses the diagram's class blocks and compares enum members, attributes, method names and parameter names with the real classes (via `dataclasses.fields` and `inspect`). Result: no differences across all 10 classes. It also found two design gaps the diagram did not show: `Task` equality (identical tasks compare equal and are unhashable) and two overlapping availability fields on `Owner`.
7. Asked to apply the two suggested fixes. The agent added a `uuid`-based `Task.id`, changed `Pet.edit_task` / `remove_task` to take `task_id`, documented that `Owner.day_start`/`day_end` is the source of truth with `available_minutes` as an optional extra cap, and updated the UML to match. It also moved a Mermaid `%%` comment it first placed inline onto its own line, since inline comments in a class member are likely to break parsing. Re-ran the comparison script (no differences across all 10 classes) and confirmed identical-field tasks now compare unequal.
8. Asked to review `pawpal_system.py` for missing relationships and logic bottlenecks. The agent reviewed the stubs and ran a small script to confirm its suspicions rather than only asserting them: `Pet` has the same equality problem `Task` had, `datetime.time` supports neither subtraction nor adding a `timedelta`, `Priority("high")` raises (the starter `app.py` passes lowercase strings), and plain attribute assignment accepts invalid values such as a negative duration. No code was changed in this step; findings were reported for the user to prioritize.
9. Asked to apply all suggested fixes and to document them, specifically in section 1b of `reflection.md`. The agent rewrote `pawpal_system.py` and `diagrams/uml.mmd` together: recurrence fields (`start_date`, `last_completed`), `Pet.id`, `PetTask`, `Priority.from_str`, minutes helpers, self-validating dataclasses, `DailyPlan.warnings`, typed `preferred_times`, removal of `priority_score` and `explain_choice`, and the scheduler rules as a docstring contract. It then re-ran the comparison script and a probe script. The first run reported one difference; the cause was a flaw in the checker (`inspect.getmembers` hides custom methods on an Enum), not in the code, so it fixed the checker and re-ran it to a clean result. It also rewrote section 1b of `reflection.md` as a numbered change list instead of appending to the old paragraph.
   - Scope note: "all suggested fixes" was read as fixes 1 to 8 applied to the stubs and diagram, and the scheduler rules (9 to 15) written as documentation, since no scheduling logic existed to apply them to. Dropping `priority_score` and making `explain_choice` private were the agent's choices among the options it had offered.
10. Asked to implement `pawpal_system.py` and find an optimal way for the `Scheduler` to retrieve all tasks from the owner's pets. The agent:
    - Added `Owner.iter_tasks()`, a lazy generator over every pet's tasks yielding `PetTask` pairs, and made `get_all_tasks()` a list of it. `Scheduler.filter_due_tasks` filters while iterating, so retrieval is one pass with no intermediate list. It rejected a cached task index because `Pet.tasks` is a public mutable list and a cache could go stale.
    - Implemented all the stubbed behavior: `Task.is_due`/`mark_complete`, `Pet` and `Owner` management, `ScheduledItem`, `DailyPlan` output, and the scheduler (cap admission in sort order, fixed-time placement, free-interval tracking for flexible tasks, conflict detection, reason text).
    - Wrote `tests/test_pawpal_system.py` (53 tests, later renamed by the user to `tests/test_pawpal.py`) and `pytest.ini`.
    - First test run: 36 failures. It read the actual failure instead of changing the scheduler, found that the cause was the tests (tasks default to today's `start_date`, tests plan for a March date, so nothing was due), and fixed the test helper.
    - Because the first run had failed for a test-side reason, it mutation-checked the tests: it broke five behaviors one at a time in a scratch copy (sort ignoring `required`, no gap search, no flagging, weekly ignoring the weekday, no cap check) and confirmed each was caught, with the real code at 53 passed.
    - Re-ran the UML comparison script (no differences) after adding `iter_tasks` to the diagram.
    - Correction (see step 11): the `iter_tasks()` design described in the first bullet was later replaced, because the Scheduler ended up bypassing `get_all_tasks`.
    - Scope note for the agent's own choices: the cap is applied in sort order before placement (a decision made while writing the loop, with a documented downside), and `from_str`, the time helpers and the validation are real code from the earlier step.
11. Pasted the project's component requirements (Task, Pet, Owner, Scheduler) and asked to double check the implementation against them. The agent checked each component against the code, and instead of only reading it, ran a spy `Owner` subclass to see which method the Scheduler really calls. Findings:
    - **Scheduler (gap, fixed):** it called `owner.iter_tasks()` and never `get_all_tasks`, so it did not read through the required single Owner method. This was a flaw in the agent's own previous step. It removed `iter_tasks`, made `get_all_tasks` the only retrieval method, and updated the UML, tests and docs. It also acknowledged this walks back its earlier claim that the lazy iterator was the optimal design.
    - **Task (gap, fixed):** completion status could only be read as the raw `last_completed` date. It added `Task.is_completed(on)` and refactored `is_due` to use it.
    - **Pet and Owner (met):** `Pet` stores details and a task list; `Owner` manages multiple pets and `get_all_tasks()` returns every pet's tasks together.
    - **Left as is, reported to the user:** the Task activity text is named `title`, not `description`, and Task has no single `time` field (it has `fixed_time`, `preferred_start` and `duration_minutes`); `get_all_tasks()` returns `PetTask` pairs, not bare `Task` objects.
    - Verification: 55 tests pass (2 new, 2 rewritten), the UML comparison is clean, and a new mutation (Scheduler bypassing `get_all_tasks`) is caught by exactly the new spy test; a mutation reading only the first pet is caught by 33 tests.
12. Asked to add a `description` field (the one naming gap left from step 11). The agent added `Task.description: str = ""` after `required` so positional arguments are unaffected, added it to the editable fields, the UML and a new test, and re-ran the tests (56 passed) and the UML comparison (clean). It did not add the field to `explain()` or `to_table()`, since the UI is not wired yet; that is noted in `reflection.md` as a later decision.
13. Asked to write `main.py` that imports the classes, creates an owner and at least two pets, adds at least three tasks at different times, and prints "Today's Schedule". The agent wrote it with one owner (07:00-20:00), two pets (a dog and a cat) and six tasks: two fixed-time (heart medication at 08:00, which is required, and lunch at 12:00) and four with preferred start times (07:30, 09:00, 15:30, 18:00). It runs `Scheduler.generate_plan(date.today())` and prints each item with its time range, duration, priority, optional description and the scheduler's reason, followed by any skipped tasks, warnings and the summary. It ran the script and got a six-item schedule with nothing skipped. The demo data was chosen so that everything fits, so the output does not show the skip, flag or warning paths (those are covered by the tests).
14. Asked to put the terminal output of `main.py` into the README's Sample Output section as evidence that the system runs. The README already had a "Sample Output" section holding a placeholder, so the agent filled that section in instead of adding a second one. It re-ran `main.py` (exit code 0) to get fresh output, pasted it as a fenced block, and then checked programmatically that the block is character-for-character identical to the output of a new run. It added two sentences of context: the header date changes with the day the script is run, and this run is the happy path (nothing skipped), with the skip, flag and warning cases covered by the tests.
15. Asked to edit `tests/test_pawpal.py` to test two behaviors: `mark_complete()` changes a task's status, and adding a task to a Pet increases its task count. The agent first checked the file's state, because the opened file was the full suite under a new name (the earlier `test_pawpal_system.py` no longer existed; the user had renamed it), then added the two tests next to the existing Task tests instead of replacing the suite. Existing tests touched these behaviors but none asserted them directly, and none asserted a task count at all. The completion test also checks a different task is unaffected; the count test also checks that a rejected duplicate does not change the count. Verification: 58 tests pass, and two deliberate bugs in a scratch copy (`mark_complete` doing nothing, `add_task` not appending) each made exactly the matching new test fail. A third mutation it tried was not aimed at these tests (it breaks the recurring-task reset, which another test covers), so it is not counted as evidence for them.
16. Asked to add one-line docstrings to the methods in `pawpal_system.py`. The agent first audited the file with a small AST script instead of guessing: 31 methods, 11 without a docstring, 7 already with a longer multi-line docstring. It added one-line docstrings to the 11 (`Task.__post_init__`, `Pet._index_of`, `Pet.remove_task`, `Owner.__post_init__`, `Owner._validate_availability`, `Owner.remove_pet`, `ScheduledItem.__post_init__`, `DailyPlan.total_minutes`, `flagged_tasks`, `summary`, and `Scheduler.__init__`) and left the existing multi-line ones alone, so nothing already documented was rewritten. Each states what the method does and, where relevant, what it raises. Verification: the audit now reports 0 missing, all 58 tests pass, the UML comparison is clean, and `main.py` output still matches the README sample exactly, which confirms the change touched no behavior. Scope: only methods; module-level helper functions such as `_fits_at` and `_carve` were not part of the request and were left as they are. The docstrings were not reviewed by the user for tone or accuracy.
17. Asked to (a) add a short implementation summary to the README, (b) complete the AI collaboration reflection in `reflection.md`, and (c) generate a commit message for the Source Control tab. The agent read the current README, reflection and `git status`/`git diff --stat` first, so the text describes what is actually in the tree.
    - README: added an "Implementation Summary" before "Getting started": what was built, how Owner, Pet, Task, PetTask, Scheduler and DailyPlan work together, and the scheduling rules. It states plainly that the Streamlit UI is not connected yet.
    - Reflection (section 3): rewrote 3a and 3b into what the AI suggested, what was accepted, what was rejected, where the AI was wrong, how it was verified, and what is still unverified. It kept to events that actually happened: only one suggestion was rejected (pushing out lower-priority tasks), the review findings were accepted as a batch, and the Scheduler bypassing `get_all_tasks` is recorded as the AI's own error.
    - Commit message: the agent cannot type into VS Code's Source Control box and was not asked to commit, so it wrote the message in the chat for the user to paste and did not run `git commit`. It matched the repo's existing `type: summary` style.
18. Pasted a three-step brief for UI and backend integration (import the classes into `app.py`; keep the `Owner` in `st.session_state`; wire form actions to the class methods and explain how the UI refreshes) and asked for it to be done. The agent:
    - Added three small backend changes first, because forms feed raw text into the classes: `Pet` and `Owner` now validate their names (and `Pet` its age), and `Owner.set_availability` takes the minutes cap so the UI can update the window and cap together with validation. It updated the UML and added tests, and re-ran the UML comparison.
    - Rewrote `app.py`: the `Owner` is created only when `"owner" not in st.session_state`; forms call `Owner.add_pet(Pet(...))`, `Pet.add_task(Task(...))`, `Pet.edit_task` and `Owner.set_availability`; buttons use `task.mark_complete`, `pet.remove_task` and `owner.remove_pet` as `on_click` callbacks; after a successful action it saves a message and calls `st.rerun()`; "Generate schedule" calls `Scheduler.generate_plan` and renders the table, warnings and explanation. It answered the brief's questions in the README (which method handles a new pet, and how the UI updates).
    - Wrote `tests/test_app.py` (15 tests) with Streamlit's `AppTest`, which runs the real script headlessly and lets the test fill forms and click buttons. It first ran an exploratory script to learn how `AppTest` addresses form buttons and enum selectboxes, instead of guessing.
    - Hit and fixed two problems on the way: `AppTest.from_file` resolves a relative path against the test file (so the tests use an absolute path to `app.py`), and the IDE flagged `labels.get` as a type error for `format_func` (replaced with a lambda).
    - Mutation-checked the UI tests with five deliberate bugs in a scratch copy. One survived: breaking the Done button's date went unnoticed because the test used a one-off task, which counts as completed on any day. It strengthened the test (daily task, exact date) and confirmed the same bug is then caught.
    - Started the real Streamlit server, confirmed `/_stcore/health` returned `ok` and `/` returned 200 with no errors in the log, and stopped it.
    - Updated the README (summary now describes the UI and how it connects; test count 75, later 78) and corrected every statement in `reflection.md` that said the UI was not connected.
    - Limits: at that point nobody had used the app in a browser (see step 19 for what the first hand test found); the agent chose the page layout and widgets itself.
19. Reported from hand-testing the UI: with the owner's max availability set to 60 minutes per day, four 20-minute tasks could still be added. The agent reproduced it with `AppTest` before changing anything, in two variants, and found two separate causes instead of one:
    - **Not a bug:** the scheduler enforces the limit. With the limit saved, the plan scheduled three tasks (60 min) and skipped the fourth. Adding tasks is not blocked by design, because the limit caps what is scheduled each day, not what can be recorded.
    - **A real UI flaw (the agent's own design):** the limit only applied if a separate "Limit total care minutes per day" checkbox was also ticked. Typing 60 without it saved no limit and all four tasks were scheduled. The agent's 15 UI tests all ticked the checkbox, so they could not catch this; the user's hand test did.
    - **Fixes:** removed the checkbox (the field is "Max care minutes per day", 0 = no limit); added `Owner.capacity_minutes()` (window length or cap, whichever is smaller) and a warning in the Tasks section as soon as today's tasks exceed it; updated the UML and README.
    - **Decision it made without asking:** warn instead of blocking the add. It said so and noted that blocking is a defensible alternative that the user can request.
    - **Verification:** 3 new tests (the exact 4 x 20 min scenario with its warning, the plan and the skip reason; the no-limit/shrunk-window case; `capacity_minutes`), one existing test updated, 78 tests passing (61 backend, 17 UI). Four deliberate bugs (warning removed, typed limit ignored, capacity ignoring the cap, scheduler ignoring the cap) were each caught.

After step 19 the whole suite is 78 passing tests (61 backend, 17 headless UI), but the app has had only a brief hand test (which found the step 19 problem) plus `AppTest` and a server start-up check, and the random tests check invariants, not plan quality.
